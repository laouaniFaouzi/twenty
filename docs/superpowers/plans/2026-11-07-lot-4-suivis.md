# Lot 4 · Suivis, rapprochement et Journal de synchro · Plan d'exécution

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un projet, ses phases et ses tâches de suivi sont synchronisés dans les deux sens avec `trackers`, `tracker_phases` et `tracker_tasks` du site. Un rapprochement toutes les 15 minutes répare les appels perdus, pour les suivis comme pour les demandes. Chaque échec est noté dans le Journal de synchro.

**Architecture:**
- **Côté site** (`interfaze-site`) : une migration ajoute `crm_id` aux trois tables et `updated_at` aux phases, passe les positions en `double precision`, et branche `notify_hubfaze()` sur les trois tables. Les suppressions en cascade ne sont pas envoyées.
- **Côté HubFaze** (app `interfaze`), quatre parties :
  - les événements `project.*`, `projectPhase.*` et `projectTask.*` poussent vers Supabase par upsert sur `crm_id` ;
  - la route `site-webhook` (lot 3) reçoit aussi les trois tables du suivi ;
  - une empreinte (`syncHash`) de l'état synchronisé sert d'ancêtre commun pour éviter les échos et trancher les conflits ;
  - une fonction planifiée `reconcile-site` compare les deux côtés.

**Tech Stack:** TypeScript, `twenty-sdk` 2.38.0, Vitest. PostgreSQL 17, `pg_net`, pgTAP. API REST de Supabase (PostgREST).

**Spec:** `docs/superpowers/specs/2026-11-04-hubfaze-crm-interfaze-design.md` (§4.2 champs techniques et Journal de synchro, §5.1, §5.4, §5.5, §5.6, §9, §11 lot 4).

## Règles de synchro (référence pour les tâches 3 à 8)

- **Empreinte** : `syncHash` = empreinte du dernier état sur lequel les deux côtés sont d'accord, calculée sur la forme « site » des champs synchronisés :
  - suivi : `client_name`, `offer`, `is_active` ;
  - phase : `tracker_id`, `name`, `position` ;
  - tâche : `phase_id`, `name`, `description`, `status`, `position`.
  `siteUpdatedAt` = `updated_at` de la ligne du site à ce moment-là.
- **Fusion** : on compare `siteHash` (empreinte de la ligne du site), `localHash` (empreinte de l'enregistrement HubFaze) et `syncHash`.
  - égales entre elles (`siteHash` = `localHash`) : rien à faire ;
  - seul le site a changé (`localHash` = `syncHash`) : on applique le site ;
  - seul HubFaze a changé (`siteHash` = `syncHash`) : on pousse HubFaze ;
  - les deux ont changé : le plus récent l'emporte (`updated_at` du site contre `updatedAt` de HubFaze), à égalité le site.
- **Modification venue du site en retard** : `updated_at` ≤ `siteUpdatedAt`, elle est ignorée.
- **Événement HubFaze** : `localHash` = `syncHash` et `siteId` déjà rempli, rien n'est envoyé. C'est ce qui arrête l'écho d'une écriture venue du site, et les modifications de champs internes.
- **Identifiants** :
  - un enregistrement créé dans HubFaze est poussé avec `crm_id` = son id ;
  - un enregistrement créé sur le site est créé dans HubFaze avec **id = id du site**, ce qui rend la création idempotente, puis `crm_id` est écrit sur le site.
- **Écritures vers le site** :
  - phases et tâches par `POST …?on_conflict=crm_id` avec `Prefer: resolution=merge-duplicates,return=representation` ;
  - suivis par `POST` (création, nouveau code), et sur `409` relecture par `crm_id` ; mise à jour par `PATCH …?id=eq.<id>` sans le code ;
  - toujours avec `x-sync-origin: hubfaze`.
- **Parent pas encore synchronisé** :
  - côté HubFaze (phase sans suivi, tâche sans phase sur le site) : l'événement est ignoré sans erreur, l'envoi de l'arbre du projet ou le rapprochement le rattrape ;
  - côté site (phase reçue avant son suivi) : le parent est relu dans Supabase et créé d'abord.
- **Suppressions** :
  - phase ou tâche supprimée d'un côté, elle est supprimée de l'autre ;
  - projet supprimé dans HubFaze, le suivi passe en `is_active = false` ;
  - suivi supprimé sur le site, le projet passe en Archivé et son `siteTrackerId` est vidé, pour qu'il ne soit jamais recréé tant qu'il reste archivé.
- **`client_name` modifié sur le site** : la société reste la référence. HubFaze applique l'offre et l'état actif, enregistre l'empreinte du site, puis son propre événement renvoie le nom de la société.
- **Erreurs** :
  - venues du site : notées `SITE_TO_CRM`, et la route répond 500 ;
  - envois de HubFaze : notés `CRM_TO_SITE`, et la fonction se termine sans relancer l'erreur ;
  - pendant le rapprochement : notées `RECONCILIATION`, et on passe à l'enregistrement suivant ;
  - dans tous les cas, le rapprochement suivant retente.

## Review Focus

1. **Écho** : une écriture appliquée depuis le site ne repart pas vers le site, et une écriture poussée par HubFaze ne revient pas. Tests en tâches 5, 6 et en intégration.
2. **Ordre d'arrivée** : une phase ou une tâche qui arrive avant son parent, dans un sens ou dans l'autre, ne crée ni doublon ni erreur (upsert sur `crm_id`, id = id du site). Tests en tâches 5 et 6.
3. **Conflit et retard** : une modification du site plus ancienne que `siteUpdatedAt` est ignorée ; en cas de conflit, la plus récente l'emporte. Tests en tâches 3 et 6.
4. **Cascade** :
   - supprimer un suivi sur le site archive le projet sans supprimer ses phases ni ses tâches ;
   - supprimer un projet dans HubFaze archive seulement le suivi.
   Tests en tâches 1, 5 et 6.
5. **Positions fractionnaires** : une tâche déplacée par glisser-déposer dans HubFaze (position 1,5) arrive sur le site sans erreur et dans le bon ordre. Tests en tâches 1 et 3.

  - `pushPhase(client, phaseId, deps)` et `pushTask(client, taskId, deps)` : `Promise<'pushed' | 'unchanged' | 'skipped'>` ;
  - `deleteSitePhase(client, phaseId, deps)`, `deleteSiteTask(client, taskId, deps)` ;
  - `archiveSiteTracker(client, projectId, deps)`.

Règles :
- **Nouveau suivi** :
  - `pushProject` crée le suivi quand le projet a une offre, n'est pas archivé et n'a pas de `siteTrackerId` ;
  - il génère le code et insère le suivi ; sur un 409, il relit par `crm_id` ;
  - puis il écrit `siteTrackerId`, `trackerUrl` (`{ primaryLinkUrl, primaryLinkLabel: 'Suivi client' }`), `siteUpdatedAt` et `syncHash`.
- **Suivi existant** :
  - `PATCH` si `localHash` ≠ `syncHash` ;
  - si le `PATCH` ne touche aucune ligne, le suivi a disparu du site : le projet est archivé et son `siteTrackerId` vidé.
- **Projet sans offre ou archivé sans suivi** : `skipped`.
- **Phase ou tâche** : `skipped` si le parent n'a pas encore d'id sur le site, `unchanged` si `localHash` = `syncHash` et `siteId` rempli ; sinon upsert, puis écriture de `siteId`, `siteUpdatedAt` et `syncHash`.
- **`on-project-changed`** :
  - à la création et quand le projet reçoit une offre : le modèle (lot 1) d'abord, puis `pushProjectTree` ;
  - à une mise à jour de `name`, `offer`, `status` ou `companyId` : `pushProject` ;
  - `deleted` : `archiveSiteTracker` ;
  - `restored` : `pushProject`.
- **Phases et tâches** :
  - `created`, `restored` et mises à jour des champs synchronisés (phase : `name`, `position`, `projectId` ; tâche : `name`, `description`, `status`, `position`, `phaseId`) : `pushPhase` / `pushTask` ;
  - `deleted` : `deleteSitePhase` / `deleteSiteTask` (par `crm_id`).
- **Sans réglages** : aucun envoi.
- **Erreur** : `recordSyncFailure(CRM_TO_SITE, …)`, puis la fonction se termine sans relancer l'erreur.
